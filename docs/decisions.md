# Decisions

> Purpose
>
> The record of why the planner has accounts, a Python API and server-side sync, and of the
> choices made while building them in October 2026, then of the calls behind its design system. The journals and pull requests cite these IDs
> (D3, P7, K5); this is where they resolve. The current design lives in
> [architecture.md](architecture.md), [api.md](api.md) and [brand.md](brand.md); this file keeps the
> reasons.

## 1. Context

Until October 2026 every log lived in one browser's `localStorage`. Data did not move between
devices, nothing was backed up, and the public route at `fitness.itsa-pizza.com` needed no auth
because nothing was on the server. The route runs Cloudflare tunnel → Traefik (rate-limited) → the
web container on infra-vm, whose port is also reachable on the LAN, so no design may trust an
unauthenticated header.

### 3.2 OAuth for claude.ai, and tokens anyone can create (2026-11-03)

Asked for by the owner: "build the oauth like home-finances. and we need any user to be able to
generate the tokens they might need to." Until now OAuth was a non-goal (the MCP page said claude.ai
could not connect without it), and tokens came from the admin CLI alone. The answers to the
owner's four questions are the plan’s D2 (URL only), D3 (90 days), D6 (a name and read or write, no expiry)
and the one Connections section (K74).

| ID  | Decision | Why |
| --- | -------- | --- |
| P31 | The authorization server is hand-written in the API, under `/api/oauth/*` (`oauth.py`, `oauth_api.py`); the MCP SDK stays the resource server only. Settled as the plan’s D1 | The SDK's `auth_server_provider` has no client ID metadata documents and no `none` client authentication. Family-finances' flow ports over without its household-key sealing or its separate MCP container. See [api.md](api.md) §3.3 |
| P32 | Clients are client ID metadata documents (CIMD) on an allow-list of hosts, `OAUTH_CLIENT_HOSTS` (default `claude.ai,claude.com`). There is no Dynamic Client Registration and no pre-registered client ID (plan D2). claude.ai and Claude Code both connect by URL alone | The MCP spec of 2026-07-28 deprecates registration, which also needs an open, unauthenticated endpoint. An allow-list leaves no open fetcher. Risk: claude.ai may still try registration, which the first real connect settles. Settled 2026-11-03: claude.ai and Claude Code both connected through their documents, with no registration ([deployment.md](deployment.md) §5.4) |
| P33 | A connection lasts 90 days from approval, absolute. An access token lasts 1 hour, never past its connection; a code 60 seconds; a replaced refresh token returns the same new pair for 60 seconds. Reusing a retired refresh token or a spent code ends the connection (plan D3) | John chose 90 days over finances' 30. The grace covers a lost reply; reuse is the signal of a stolen token |
| P34 | The consent screen shows a warning first, then the asking app's host and the redirect host, and asks for email and password even when signed in. It shares the login lockout and hash queue, leaves Read only chosen (K73), and creates no web session (plan D4) | Approval hands a program the account, so a password proves a person is there. A stolen session cookie must not be enough |
| P35 | A pending request is held server-side for 10 minutes under an id: `/api/oauth/authorize` answers 302 to `/#/connect/<id>`. The route is a link route that shows signed in or out and survives a sign-out (plan D5) | The app uses hash routing, so the consent screen needs an address of its own. The id shows in access logs; it is single use and still needs the password ([api.md](api.md) §8) |
| P36 | A person creates personal tokens in the app: a name, `read` or `write`, no expiry, shown once. At most 20 tokens and 10 connections per account; beyond that, 409 `too-many` (plan D6). The CLI mints without a limit. Supersedes the CLI-only part of P22 | John chose "name and read/write, no expiry". The caps keep a stranger's account from filling the table |
| P37 | One helper, `auth.end_credentials`, ends an account's tokens and connections, in the same transaction as a password reset, `disable` or `revoke-sessions` (plan D7) | Two code paths that each end "the credentials" drift apart; one cannot leave a connection alive |
| P38 | Tokens carry a kind prefix: `trk_` personal, `tka_` OAuth access, `tkr_` OAuth refresh. The MCP verifier dispatches on it, checks expiry on the server clock, returns the grant's stored `resource`, and answers 503 rather than 401 when its lookup fails (plan D8) | A prefix sends a lookup to one table. A 401 tells Claude the connection is gone, so a database error must not look like one |
| P39 | ChatGPT connects as a third CIMD client: `chatgpt.com` joins `OAUTH_CLIENT_HOSTS`, and a document is a public client when its `token_endpoint_auth_method` is `none` or its `token_endpoint_auth_methods_supported` list holds `none`. No `private_key_jwt`, no pre-registered client, and no Cloudflare change until a connect shows one is needed (2026-11-04) | ChatGPT's document prefers `private_key_jwt` and lists `none`; OpenAI says a server should accept any method in the intersection, which here is `none`. Verifying signed assertions would add a fetch of OpenAI's keys and a JWT check for no gain over PKCE. Family-finances, with no CIMD, pre-registered ChatGPT instead (its ADR-0049); the tracker already reads documents, so its P32 holds. See [api.md](api.md) §3.3 and [deployment.md](deployment.md) §5.5 |

Not decided here: OAuth for REST routes (a token opens only `/api/mcp`), token expiry for
personal tokens, and anything about sign-up or invites, which already allow many users.

## 5. Accepted risks

Each is described where it applies:

- the lockout and sign-up reveal which emails have accounts; the lockout can block
  one; sessions have no absolute lifetime; anyone can claim an email that is not theirs until it is
  confirmed; whoever holds an account's inbox can reset its password; Resend sees the addresses and
  links; strangers can fill the account cap or the hourly limit, or the 1,000 pending connection
  requests, and a pending request's id shows in access logs ([api.md](api.md) §8);
- two tabs racing on the shared outbox inside Chrome's cross-process delay, and a session that ends
  by itself keeping its cache ([architecture.md](architecture.md) §7);
- while the API restarts, Docker's DNS can forward the web container's `fitness-api` lookup to the
  LAN resolver (home-server `documentation/infra_vm.md`, "Fitness").
